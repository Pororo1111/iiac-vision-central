# 쓰러짐 탐지: Jetson 포즈 판정 + 중앙 Gemma 2차 확인 (2026-10-10)

## 결정

- 사용자 결정: 쓰러짐 1차 판정은 현장 장치(Jetson Orin Nano)에서 한다. 방식은 B안(포즈 모델 + 규칙)이다.
- 박스 비율만 보는 A안은 내려다보는 각도와 허리 굽히기에 약하다. 새 클래스를 학습하는 C안은 데이터가 필요하고 기준 test 하락 위험이 있다. 시계열 분류기를 쓰는 D안은 Nano에는 무겁다. 그래서 세 안 모두 채택하지 않았다.
- 장치가 쓰러짐을 확정하면 그 순간의 원본 사진 1장을 중앙으로 보낸다. 중앙 Gemma 장면 판정(`fallen`, V31)이 2차 확인을 한다. 오경보 가능성은 표시하되, 알림 자체는 Gemma 결과와 관계없이 바로 띄운다.

## 흐름

| 순서 | 현장 장치(IoT 구현 대상) | 중앙(구현됨) |
|---|---|---|
| 1 | 사람이 보이는 프레임마다 `yolo26n-pose`(TensorRT FP16 권장)로 17개 키포인트를 구하고 ByteTrack으로 추적한다. 규칙 판정은 10fps 이상으로 돌린다 | – |
| 2 | `scripts/fall_rules.py` 규칙으로 FALL_START를 확정한다 | – |
| 3 | `POST /api/iot/events`로 `FALL_START`를 보낸다. zoneId는 생략하고, objectCount는 쓰러진 사람 수다 | 이벤트를 저장한다(관제 화면 알림은 2026-10-12 제거, 아래 화면 노출 절) |
| 4 | 같은 UUID를 batchId로 써서 프레임 1개짜리 탐지 배치를 보낸다(`startedAt=at`, `endedAt=at+1ms`, 사람 박스) | 원본 사진 1장을 기다리는 구간 작업을 만든다. 쓰러짐 작업은 대기열에서 먼저 처리된다 |
| 5 | 같은 batchId와 `at`으로 오버레이 없는 원본 1장을 보낸다(`/api/iot/detection-snapshots`) | Gemma 장면 판정 결과가 이벤트의 `fallCheck`가 된다 |
| 6 | 일어나 서 있는 상태가 2초 이어지거나 5초 넘게 사람이 안 보이면 `FALL_END`를 보낸다 | 기록만 남긴다 |

## 화면 노출 (2026-10-12)

- 사용자 결정: 현재 쓰러짐 정확도가 낮아 통합 관제 화면에서 쓰러짐 알림·이벤트(목록·유형 필터)를 제거했다. 관제 화면은 `GET /api/events?intrusionOnly=true`로 침입 이벤트만 조회한다.
- 쓰러짐은 `/video-search` 대화에서 질문할 때만 본다(예: "쓰러진 사람 있어?" → `fallen=true` 조건, Gemma 장면 판정 `fallen>0` 구간).
- 이벤트 저장·Gemma 2차 확인·`/api/alerts/falls`·확인 처리 API는 그대로 둔다. 제거 시점 FALL_START 15건 중 Gemma가 쓰러짐으로 판정한 구간은 0건이다(완료 11·생략 4).

## 판정 규칙(`scripts/fall_rules.py`)

표준 라이브러리만 쓰는 참고 구현이다. IoT는 이 파일을 그대로 쓰거나 같은 규칙으로 옮겨 구현한다.

| 단계 | 규칙 | 기본값 |
|---|---|---|
| 자세 | 신뢰도 0.3 이상 키포인트가 5개 이상이면 키포인트 가로/세로 폭 비율을 쓰고, 아니면 박스 비율만 쓴다. 키포인트 비율 ≥ 1.2이거나 박스 비율 ≥ 1.1이면 누움, 둘 다 < 0.8이면 서 있음, 그 사이는 애매로 본다 | `lying_kp_ratio` 1.2, `lying_box_ratio` 1.1, `upright_ratio` 0.8 |
| 전이 | 같은 추적 ID(없으면 서 있던 박스를 좌우로 키만큼, 아래로 20% 넓힌 영역과 겹치는 사람)가 1.5초 안에 서 있음 → 누움으로 바뀌면 후보로 본다. 처음부터 누워 있던 사람이나 천천히 눕는 경우는 제외한다 | `transition_seconds` 1.5 |
| 확정 | 후보가 누운 상태를 유지하면 FALL_START로 확정한다. 관측의 60% 이상이 누움이고 3회 이상 관측되어야 한다. 포즈 모델이 누운 사람을 놓쳐도 5초까지 후보를 유지하고, 추적 ID가 바뀌어도 박스가 겹치면 같은 후보로 본다 | `hold_seconds` 운영 2.0, 검증 1.0 |
| 종료 | 확정 뒤 서 있음이 2초 이어지거나 5초 넘게 관측되지 않으면 FALL_END를 낸다 | `recover_seconds` 2.0, `lost_seconds` 5.0 |

- 지원 시점은 옆 또는 비스듬한 시점(일반 CCTV·웹캠)이다. 천장에서 수직으로 내려다보는 시점은 지원하지 않는다. 앉은 사람도 가로로 넓게 보여 '서 있음'으로 관측되지 않기 때문이다.
- 처음 쓰러짐 판정을 받는 현장에서는 운영 기본값 `hold_seconds=2.0`으로 시작하고, 오경보와 지연을 보고 조정한다.

## 검증 데이터

- Roboflow Universe의 URFD(UR Fall Detection) 프레임 데이터셋 2개를 받았다(둘 다 CC BY 4.0). 하나는 `fall-older/ur-fall-detection-dataset-mbbxe` v1(2,600장, fall/person), 다른 하나는 `elderlyfalldetectionprojectfinalizeddataset/5-urfall-0aeal` v1(909장, fall/non-fall)이다.
- 파일 이름에 원래 시퀀스와 프레임 번호(`fall-02-cam0-rgb-094`)가 남아 있다. 두 데이터셋을 합쳐 프레임이 거의 빠지지 않은 시퀀스 12개를 30fps 영상(640×480, H.264, 합계 약 6MB)으로 다시 만들었다. 비어 있는 프레임은 앞 프레임으로 채웠다.
  - 쓰러짐 7개: 옆 시점(cam0) 5개, 천장 시점(cam1) 2개. 각 3.2~7.2초.
  - 일상 동작(ADL) 5개: 걸어와 쪼그려 앉기, 바닥 물건 줍기, 허리 굽히기. 각 5~6초.
- 프레임별 정답은 Roboflow 라벨(fall 클래스)을 썼다.
- 작업 파일은 `.artifacts/fall-eval/`(Git 제외)에 있다. `videos/`, `gt.json`, 포즈 추출 결과 `pose-*.json`, `bench.py`, `gemma_check.py`, `gemma-check.json`, 프레임 묶음 `sheets/`.
- 영상이 짧아 쓰러진 뒤 누운 시간이 1.0~2.2초뿐이다. 그래서 운영값 `hold_seconds=2.0`은 이 영상으로 검증할 수 없었고, 검증은 1.0으로 했다.

## 결과

| 항목 | 결과 |
|---|---|
| 규칙(맥, yolo26n-pose, 30fps, hold 1.0) | 옆 시점 쓰러짐 5/5 탐지. 확정 지연은 정답 첫 쓰러짐 프레임 기준 +0.7~+1.4초. ADL 오탐 0/5, 천장 시점 0/2(미지원) |
| yolo26s-pose | 같은 결과(5/5, 0/5). 프레임 단위 누움 재현율이 조금 높다(tp 241 대 217) |
| 프레임 수 | 30fps와 10fps는 같은 결과였다. 5fps에서는 옆 시점 3/5로 떨어졌다(30fps 추적 결과를 솎아 낸 근사값). 10fps 이상을 권장한다 |
| 프레임 단위 누움 판정 | ADL 프레임 중 누움 0. 정답과 어긋난 것은 쓰러지는 도중의 경계 프레임과 천장 시점 앉은 자세였다 |
| Gemma 2차 확인(`segment-v6`, 사진 1장) | 규칙이 확정한 순간의 사진: 쓰러짐 5/5 `fallen=1`. 천장 시점 마지막 프레임도 2/2 `fallen=1`. ADL 마지막 프레임(쪼그림·엎드림) 0/5(전부 `fallen=0`). 장당 약 9~13초 |
| 중앙 끝까지 | `scripts/simulate-fall-iot.py`로 fall-02·fall-05·adl-01을 테스트 백엔드 8211로 보냈다. 쓰러짐 2건 모두 15초 안에 `CONFIRMED`, ADL은 이벤트 없음. 쪼그린 장면을 일부러 FALL_START로 보낸 경우 `NOT_CONFIRMED`로 바뀌었다 |
