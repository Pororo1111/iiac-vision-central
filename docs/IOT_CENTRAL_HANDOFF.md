# IoT → 중앙 수집 이미지 연동 개발 요청

> 현재 구조와 접속 주소는 [통합 아키텍처](ARCHITECTURE.md)를 따른다. 아래는 시점별 점검·개발 요청·검증 기록으로, 이전 SAM3·수동 프롬프트·Nginx 개발 경로 설명을 현재 기능으로 해석하지 않는다.

> 2026-09-26 업데이트: 이 문서의 원본 수집·학습자료 전달 계약은 계속 유효하다. 별도 확장으로 중앙 등록·heartbeat와 실시간 웹캠 송출·카메라 상태 보고를 구현했고, 실제 Jetson → MediaMTX → 중앙 관리자 브라우저 WebRTC 재생을 확인했다. 아래의 “원격 확인 결과”는 개발 전 2026-09-25 기준선이다.

작성일: 2026-09-25. 대상: `~/iot-server`, 확인 커밋 `b745f47`.

## 목적

현장에서 수집한 이미지를 중앙 서버에 누적하고, 중앙 관리자가 이미지들을 선택해 자유 프롬프트로 Gemma 12B 분석을 실행한다. 유니폼 전용 기능이 아니다. 중앙 화면에는 수동 이미지 업로드와 기준 유니폼 사진 기능이 없다.

이 문서는 개발 요청과 계약이다. 아래 미구현 기능이 이미 작동한다고 가정하지 않는다. 이번 요청으로 원격 코드 변경이나 감시 설정 변경을 수행하지 않았다.

## 원격 확인 결과

원격 작업을 통해 현재 소스를 점검했고, 중앙에서 `http://<iot-ip>:8100`의 `/health`, `/ready`, `/api/status`, `/api/config`, `/openapi.json`을 읽기 전용으로 확인했다. 자세한 근거는 `IOT_CURRENT_IMPLEMENTATION.md`에 있다.

| 항목 | 현재 구현 | 근거 |
|---|---|---|
| 장치 | `iot-jetson-001`, Jetson/CUDA 워커, 모델 `ppe4-rf27-local-m-20260914` | `/api/status`, 원격 README |
| 영상 추론·영역 | 웹캠/영상 입력, YOLO 탐지, 라바콘 영역과 침입 판별 | `worker/main.py: main()`, `worker/zones.py` |
| 이미지 | 박스·영역을 그린 최신 JPEG 한 장만 메모리에 보관 | `worker/main.py: main()`, `app/main.py: ingest()` |
| 미리보기 | `GET /api/snapshot`, 원본·누적 목록 없음 | `app/main.py: preview()` |
| 저장 | SQLite의 settings·events, 주기적 침입 기록 최근 1,000개 | `app/main.py: lifespan(), ingest()` |
| 중앙 연결 | 등록·heartbeat·이벤트·이미지 전송 및 영구 outbox 미구현 | `worker/main.py: Connection`, `central_connected=False` |
| 감시 상태 | 점검 당시 `enabled=false`, paused, `/ready` 503 | 설정에 따라 중지된 상태이며 API 자체는 `/health` 200 |

**누적 저장된 수집 이미지는 현재 0장이다.** `frames_processed`는 추론 횟수이며 수집 이미지 수가 아니다. 메모리 스냅샷을 누적 데이터처럼 표시하거나 과거 프레임을 복원할 수 있다고 설명하지 않는다.

## 우선 구현 순서

### 1. 원본 이미지의 영구 수집

- `result.plot()` 이전의 원본 프레임을 JPEG 또는 PNG 파일로 저장한다. 박스·라바콘 영역이 그려진 미리보기는 별도 용도다. 학습 입력에 오버레이 이미지를 섞지 않는다.
- 촬영 시점에 불변 `capture_id`(UUID), `device_id`, `camera_id`, UTC `captured_at`을 생성한다. API 도착 시각이나 재전송 시각으로 바꾸지 않는다.
- 파일을 임시 경로에 쓴 뒤 atomic rename하고 SQLite에 수집 정보를 기록한다. 중간 종료 시 파일·DB 불일치를 점검하고 복구한다.
- 최소 메타데이터: 위 식별자, 원본 경로·SHA-256·가로/세로·형식·바이트 수, 수집 사유, 사용 모델명·해시, 소스 종류, 설정 revision. 탐지 결과·영역 ID/좌표는 별도 JSON으로 보존한다.
- 수집 조건은 설정 가능하게 한다. 정해진 간격, 침입 시작, 낮은 탐지 확신 등으로 샘플링하고 동일 장면 반복 저장을 줄인다. 특정 유니폼이나 person 검출에만 제한하지 않으며 음성 샘플(대상이 없는 장면)도 수집할 수 있어야 한다.
- 수집·디스크 I/O·전송 대기가 추론 루프를 막지 않도록 큐/작업자를 분리한다. 기본 수집 빈도·디스크 한도·보관 기간을 문서화한다.

### 2. 중앙 장치 연결

- 환경 설정: `CENTRAL_BASE_URL`, `DEVICE_ID`, `CENTRAL_DEVICE_TOKEN`, HTTP 타임아웃. 기존 `WORKER_TOKEN`은 로컬 워커 인증용으로 유지한다.
- 중앙 주소: `https://<central-host>:9443`. Tailscale 연결과 TLS 인증서 검증을 유지한다.
- 중앙에 `iot-jetson-001`을 사전 프로비저닝하고 같은 장치의 토큰을 안전하게 전달받은 뒤 연결한다. 현재 개발 환경의 기본 seed ID를 원격 장치 ID라고 가정하지 않는다. 토큰은 문서·Git·로그·브라우저에 넣지 않는다.
- 시작 시 `POST /api/iot/register`, 이후 5초마다 `POST /api/iot/heartbeat`를 전송한다.
- `RUNNING`, `STOPPED`, `STALE`, `ERROR`, `UNKNOWN`으로 실행 상태를 매핑한다. 설정 `enabled=false`는 STOPPED, 활성인데 워커 보고가 끊기면 STALE이다. 온라인 여부는 중앙의 마지막 수신 후 30초 기준이다.

요청 예시(인증 헤더 값은 별도 주입):

```json
{"deviceId":"iot-jetson-001","name":"현장 Jetson"}
```

```json
{"deviceId":"iot-jetson-001","modelName":"ppe4-rf27-local-m-20260914","runtimeStatus":"STOPPED"}
```

### 3. 이미지 영구 outbox와 중앙 전송

중앙에 **현재 구현된 수신 계약**은 다음과 같다. 이 계약으로 최소 연동을 먼저 구현한다.

| 항목 | 계약 |
|---|---|
| Method / Path | `POST /api/iot/training-samples` |
| 인증 | `Authorization: Bearer <장치별 중앙 토큰>` |
| 본문 | `multipart/form-data` |
| `file` | 원본 JPEG/PNG, 최대 10MiB, 최소 32×32, 최대 20,000,000픽셀 |
| `title` | 비어 있지 않은 설명, 최대 160자 |
| `deviceId` | 사전 인증 장치와 일치, 최대 64자 |
| `cameraId` | 재시작에도 안정적인 카메라 ID, 최대 64자 |
| `capturedAt` | 촬영 시각 UTC ISO 8601, 예: `2026-09-25T08:45:51.329634Z` |
| 성공 | HTTP 200, JSON의 `id`를 중앙 샘플 ID로 보관 |
| 재전송 | 같은 장치·카메라·촬영 시각·이미지 내용이면 HTTP 200 및 동일한 `id` |

중앙은 이미지의 실제 형식과 픽셀 수를 검사하고 메타데이터를 제거한 JPEG로 저장한다. 중복 키는 **deviceId + cameraId + capturedAt + 정규화된 이미지 SHA-256**이다. 최초 업로드한 파일 바이트와 촬영 시각을 재시도 중 변경하지 않는다. 서버가 반환하는 `sha256`은 원본 파일 해시와 다를 수 있다. 중앙 `id`와 로컬 `capture_id`도 다른 값이다.

성공 응답의 사용 필드 예시:

```json
{"id":"<중앙 UUID>","deviceId":"iot-jetson-001","cameraId":"usb-0","status":"NEW","createdAt":"<중앙 수신 시각>"}
```

- 로컬 파일과 전송 대상을 SQLite outbox에 먼저 저장한 뒤 별도 sender가 전송한다.
- 200 응답과 유효한 중앙 UUID를 확인했을 때만 완료로 변경한다. 응답이 유실되어 재전송해도 같은 중앙 ID로 수렴해야 한다.
- 네트워크 오류·5xx·429는 상한과 jitter가 있는 지수 백오프로 재시도한다. `Retry-After`가 있으면 반영한다.
- 401/403은 설정 문제로 표시하고 짧은 간격으로 반복하지 않는다. 400/413/415는 잘못된 파일·메타데이터를 격리하고 실패 사유를 남긴다. 그 밖의 오류도 오류 내용을 보존해 운영자가 확인할 수 있게 한다.
- 중앙 종료 중에도 현장 추론과 로컬 수집을 유지하고, 프로세스·기기 재시작 후 미전송 항목을 복구한다.
- 미전송 파일은 일반 보관기간 정리로 삭제하지 않는다. 용량 한계 시 새 수집을 제한하고 그 상태를 명시한다. 전송 완료 파일부터 보관 정책에 따라 정리한다.

`captureId`, 원본 해시, sourceKind, 수집 사유, 모델/설정/영역·탐지 메타데이터는 **현재 중앙 수신 API의 지원 필드가 아니다.** 먼저 로컬에 보존하고, 중앙 API·DB를 확장하는 후속 계약으로 합의한다. 현 API가 해당 필드까지 저장한다고 가정하지 않는다.

### 4. 수집·전송 현황 API와 화면

아래는 **IoT에 새로 만들 것을 요청하는 API**이며 현재 존재하지 않는다.

- 수집 이미지 목록: captureId, 촬영 시각, 카메라, 수집 사유, 썸네일, 전송 상태, 중앙 ID; 필터·페이지 조회.
- 원본 조회와 오버레이 조회를 구분한다. 임의 파일 경로 입력을 받지 않는다.
- 집계: 저장 건수·바이트, 전송 대기·실패·완료, 가장 오래된 미전송 시각, 마지막 성공/실패·다음 재시도 시각.
- `central_connected`를 상수가 아닌 최근 실제 통신 결과로 계산하고 연결·추론 상태를 분리한다.
- 보관 정책·수집 사용 여부·빈도를 조회/변경할 수 있게 하되 기존 제어 API의 인증·교차 사이트 보호를 유지한다.
- 미전송 자료 삭제는 경고와 명시적인 사용자의 선택이 필요하다. 일반 정리는 전송 완료 파일에만 적용한다.

### 5. 침입 상태 전이 이벤트 연동

현재 30초 간격 로컬 로그와 별개로 침입 시작/종료 상태 전이를 만들고 `/api/iot/events`로 전송한다.

```json
{"eventId":"<최초 생성한 UUID>","deviceId":"iot-jetson-001","cameraId":"usb-0","zoneId":"zone-0","type":"INTRUSION_START","occurredAt":"<UTC ISO 8601>","objectCount":1}
```

종료는 `INTRUSION_END`이다. UUID·발생 시각은 재시도에도 동일하게 유지한다. 중앙 200의 `duplicate:true`도 전송 성공이다. 워커 중단·stale·카메라 오류를 정상적인 침입 종료로 처리하지 않는다. 이벤트 outbox는 로컬 이력 최근 1,000건 정리에서 제외한다.

## 중앙에서 이미 구현한 범위

- 장치 Bearer 인증, 등록·heartbeat·이벤트, 이미지 수신·재전송 중복 방지.
- 수집 이미지 현황·장치/상태 필터·집계·페이지 조회. 직접 업로드 UI/API는 제거했다.
- 1~40개 선택 → 프롬프트 입력 → 이미지별 Gemma 12B 작업 → 결과/태그·작업 이력 → 관리자 확인/제외.
- 작업 큐·워커 임대·타임아웃·중복 작업 차단·결과 이력 저장.
- 원격 데이터의 능동 조회/동기화, 원격 이미지 삭제, SAM3, YOLO 재학습·평가·자동 배포는 미구현이다.
- 로컬 개발은 Docker를 사용하지 않는다. 중앙 DB 55432와 backend 8201은 loopback 전용이며 원격은 위 HTTPS 주소만 사용한다.

## 완료 검증

1. 실제 카메라 원본을 수집하고 API·워커 재시작 뒤에도 파일과 메타데이터가 남는지 확인한다.
2. 등록 → heartbeat → 실제 이미지 수집 → 중앙 현황 반영 → 프롬프트 작업 → 결과 조회를 끝까지 확인한다.
3. 중앙 중단 중 추론·수집이 계속되고 복구 후 전송되는지 확인한다. 성공 응답 유실·중복 전송에도 중앙 샘플은 한 개여야 한다.
4. 다른 장치 ID·잘못된 토큰·손상 이미지·용량 초과·네트워크 타임아웃을 검증한다.
5. 보관기간 정리에서 미전송 파일이 보호되고 저장 공간 부족이 화면에 표시되는지 확인한다.
6. 감시 중지/stale가 침입 종료로 오보고되지 않고, 장치 연결 상태가 실제 heartbeat에 따라 변하는지 확인한다.
7. 테스트 데이터는 별도 테스트 장치에 생성하고 검증 종료 시 제거한다. 실제 수집량을 테스트 이미지로 채우지 않는다.

현재 수집이 중지된 설정을 임의로 켜거나 테스트 영상을 실제 현장 데이터로 전송하지 않는다. 원격 구현 작업을 시작할 때 이 문서의 계약과 장치 프로비저닝을 먼저 맞춘다.

## 2026-09-27: 모델 배포 계약과 현장 코드 상태

중앙은 [API 계약](API.md#iot-모델-배포-계약-2026-09-27)의 desired·model·status를 구현했다. 실제 PostgreSQL·임시 장치로 인증 분리·전이·해시·재전송을 검증했다.

IoT 기존 채팅에서 명시적 CLI 배포 클라이언트를 구현했다. 자동 폴링은 없고, 동일 HTTPS origin·크기·SHA-256·클래스·후보 추론을 확인한 뒤 버전 디렉터리와 원자적 링크 전환을 사용한다. 중단·실패 시 이전 모델 복구, 모델과 메타데이터의 같은 버전 로드를 구현했다. IoT 보고 기준 전체 단위 테스트 55개, 문법·diff 검사를 통과했다. 변경은 원격 작업트리에 있으며 커밋하지 않았다.

실제 중앙 모델 다운로드·Jetson GPU 후보 검증·현장 적용은 하지 않았다. API·워커 서비스는 기존 실행을 유지하고 새 코드를 서비스에 반영하지 않았다. 당시 구현 보고는 감시 일시중지·원본 수집 설정 켜짐·활성 모델 링크 미생성이었다. 이후 2026-09-27 12:11 KST 원격 점검에서는 감시·원본 수집·영상 송출이 실행 중이며 5초 간격 수집 기록 증가를 확인했다. 과거 중지 기록을 현재 상태로 간주하지 않으며, 후속 개발은 운영 설정을 그대로 보존한다. 현장 적용 전 새 API·워커 코드 반영과 별도 통합 검증이 필요하다.

### 같은 날 중단 후 재개한 실제 연동 검증

원격 IoT에서 검증 전용 장치와 프록시로 실제 중앙 HTTPS의 배포 조회·가짜 파일 다운로드·해시·FAILED 보고·종료 다운로드 차단을 확인했다. 이벤트 START/END와 테스트 영상 이미지 1건은 503·응답 유실 후 재전송해 중복 없이 저장됐다. 중앙 DB에서도 START/END 각 1건, 이미지·완료 작업 각 1건을 확인하고 검증 자료를 정리했다. 운영 서비스는 중단하지 않았으며 실제 모델 로드·GPU 검증·현장 적용은 여전히 미검증이다.

### 사용자 요청에 따른 작업 중단·인계

- 원격 최종 커밋은 `c137838`이며 배포 CLI·중앙 계약 검증을 포함한다. Python 테스트 56개 통과. 앞 절의 미커밋·55개 기록은 이전 시점이다.
- `worker/spool.py`는 미완성·미추적 상태로 보존했다. 다음 작업은 워커 연결, 디스크 보관·재시작 복구·중복 처리·용량 한도 검증이다.
- 수집 화면 브라우저 검증은 완료하지 않았다. 원격 Node가 없어 화면 스크립트 검사도 실행하지 못했다.
- 마지막 원격 상태 조회는 `paused`, `enabled=false`, `/ready` 503이었다. 운영 smoke test 미통과를 기록하며 감시 재개나 서비스 재시작으로 해결하지 않았다.
- 중앙 미커밋 변경을 보존한다. 추가 구현·현장 적용은 중단했고 [개발 현황](DEVELOPMENT_PLAN.md)의 순서로 재개한다.
